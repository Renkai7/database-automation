<objective>
Drive one thin, production-quality path through every layer this phase touches — shared environment
validation, Drizzle schema, a generated and applied migration, a deterministic seed, a Next.js
Server Component that queries Drizzle directly (D-05), and a headless HTTP assertion (D-08) — then
expand that path with the environment layer's failure states (D-20, D-21).

Purpose: proving the whole stack end-to-end on one recipe row, before any horizontal build-out,
catches an architectural dead end after one commit rather than after ten. ENV-02's documented loop
and APP-01's "the application boots against the resulting schema" are both settled here, on the
narrowest possible surface.

Output: `scripts/env.ts` with its test suite, the recipes table and its first migration, a seeded
recipe row, a working `/recipes/[slug]` route, and `tests/smoke.test.ts` — the scriptable boot proof
that Phase 4 (RUN-07) and Phase 5 (CI-01) reuse verbatim.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| process environment → every database-opening process | An ambient or platform-injected connection variable decides which database a command actually reaches |
| browser request → Next.js Server Component | The `slug` route segment is attacker-controlled input that reaches a database query |
| database dump / restore boundary → environment identity | A marker that travels inside the dump payload can assert the wrong environment after a restore |
| application process → stdout, stderr, error pages | Anything rendered or logged on a failure path can leak the connection string |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-06 | Tampering | `scripts/env.ts` connection resolution | high | mitigate | Bare-variable rejection throws before the schema parse, and `assertDevelopmentDatabase` re-checks `current_database()` on the live connection; both are covered by `scripts/env.test.ts` |
| T-01-07 | Spoofing | environment identity across a restore | high | mitigate | The marker is `current_database()`, a property of the connection target, not a row inside the dump payload (D-21, RESEARCH Pitfall 2) |
| T-01-08 | Tampering | `slug` route segment reaching a query | medium | mitigate | The route queries through Drizzle's query builder, which parameterises; no string-built SQL appears in `page.tsx` |
| T-01-09 | Information Disclosure | thrown messages and Next.js error output | high | mitigate | Error messages are constructed from database names only; a test asserts no thrown message contains a connection-string scheme prefix. Production `next start` (not `next dev`) is what the smoke test exercises, so stack traces are not rendered to the client |
| T-01-10 | Denial of Service | an unbounded query from a route | low | accept | The route reads one row by unique slug against a disposable local database with no external traffic; statement and lock timeouts are Phase 4's RUN-03, deliberately not built here |
| T-01-SC | Tampering | npm installs | high | mitigate | package-legitimacy gate + blocking human checkpoint for [ASSUMED]/[SUS] — resolved at plan 01-01 Task 2; this plan pins the approved versions and commits the lockfile |
</threat_model>

- The environment marker shape (left open by D-21) is `current_database()`. Rationale: D-21's own
  binding constraint is that a restore must not carry a stale marker; a stored row travels inside

  so the servings scaler's multiplier derives from a real column.
- The route key is a `slug` rather than the generated `id`, so the deterministic seed produces a
  stable URL the headless smoke test can request without a lookup step.
