# Phase 1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** Phase 1's entire UI surface is exactly one screen — `Recipe Page` — ported
verbatim from `apps/recipe-app/design/Recipe Page.dc.html` and wired to real database rows
(CONTEXT.md D-06, D-08). `Kitchen Home`, `Meal Planner`, and `Recipe Builder` stay as unported
design files (D-07) and are out of scope for this contract. Per D-06/D13, the UI is **imported
as-is** — this document records the contract the source file already encodes; it does not
propose a new design direction.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | none — plain HTML/CSS. The source's `<sc-if>`/`<sc-for>`/`{{ }}`/`DCLogic` binding model is ported to React components/hooks; no Radix, Base UI, or shadcn is introduced. |
| Icon library | none — hand-authored inline SVG (stroke-based, 24×24 viewBox, `currentColor`), copied verbatim from the source markup. The Modernist readme's general "use Lucide" guidance does **not** apply to this screen; `Recipe Page.dc.html` already deliberately departs from Modernist (D-06) and its icons are not Lucide imports. |
| Font | Archivo, loaded in source via `@import url('https://fonts.googleapis.com/css2?family=Archivo:wght@400;600;800&display=swap')` (`_ds/.../styles.css` line 2). Recommended Next.js equivalent: `next/font/google` with `weight: ['400','600','800']` — same three weights, no visual difference, avoids a render-blocking `@import`. |

**Why no shadcn:** D-06 and D13 are locked decisions — the UI comes from a Claude Design
hand-off and is brought over "without design changes," and "backend stays thin." Introducing a
component library here would mean re-implementing the ported screen's already-fixed visuals in
someone else's primitives, which is exactly the normalization D-06 forbids. The shadcn
initialization gate is therefore skipped for this phase, not merely declined.

## Visual Hierarchy

**Focal point:** the recipe title (`h2`, 800 weight, 24/34/36px) is the primary visual anchor
of the screen. `Recipe Page.dc.html` has **no hero image** — line 127 of the source records
"Photo removed. The cream sheet starts just under the nav row and runs the full height." Do not
reintroduce one. Reading order after the title: subtitle → meta row (clock/effort/macro) → tab
track → active panel content → "Mark as cooked" CTA. The accent fill on the header strip and on
the CTA are the only two accent-weight draws above the fold; they bracket the content rather
than competing with the title.

## Spacing Scale

**Two regimes apply, and they must not be merged:**

1. **The ported `Recipe Page` screen** — every spacing and radius value is taken verbatim from
   `Recipe Page.dc.html` and does **not** sit on a 4px grid. This is intentional (D-06/D13:
   preserve the departure, do not "fix" it). Do not round these to the nearest 4px.
2. **Any net-new markup this phase must author that is *not* part of the ported screen** — the
   Next.js root layout shell, and whatever the recipe-not-found / error-boundary decision in
   Open Questions below produces — should use the standard 8-point scale.

### Standard scale (for net-new, non-ported markup only)

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline padding |
| sm | 8px | Compact element spacing |
| md | 16px | Default element spacing |
| lg | 24px | Section padding |
| xl | 32px | Layout gaps |
| 2xl | 48px | Major section breaks |
| 3xl | 64px | Page-level spacing |

### Recipe Page exceptions (verbatim from source — see file for the exact value at each breakpoint)

| Category | Observed values (phone / tablet / desktop) |
|----------|---------------------------------------------|
| Icon buttons (back, save) | 38px / 40px / 48–50px square, radius 14–18px |
| Favorite button | 44px / 50px / 48px square, radius 16–18px |
| Content-sheet top radius | 34px / 34px / 34px (desktop overlaps its header via `margin-top:-16px`) |
| Frame/header side padding | 18–20px / 20–28px / 40–56px |
| Ingredient card radius | 20px / 22px / 22px |
| Chip / step-number badge radius | 9–12px |
| Pills (tab track, stepper, CTA, timer chip) | `border-radius: 999px` throughout |
| Section gaps | 12–18px (small) · 20–26px (medium) · 34–56px (desktop sidebar layout) |

Exceptions: every value above is a direct transcription from `Recipe Page.dc.html`; none are
multiples of 4 (18, 14, 26, 34, 38 in particular). This is the documented, intentional
departure — not a defect to normalize.

## Typography

Sizes vary continuously across the phone/tablet/desktop breakpoints in the source rather than
the generic 3–4-size guidance — this is the source file's own scale, preserved per D-06.
Do not invent intermediate sizes; use the exact value at each breakpoint from the source file.

| Role | Size (phone / tablet / desktop) | Weight | Line Height |
|------|----------------------------------|--------|-------------|
| Display (recipe title, `h2`) | 24px / 34px / 36px | 800 (inherited from the global `h1,h2,h3,h4{font-weight:var(--font-heading-weight)}` rule in `styles.css`) | 1.15 / 1.10 / 1.08 |
| Heading (tab labels, CTA label, servings count, ingredient name, step-number badge) | 13.5–15px, varies by element and breakpoint | 700 (inline override — distinct from the 800 weight `h2` gets automatically) | 1.2 (ingredient name); single-line elsewhere |
| Body (step text, meta-row labels, servings caption) | 12.5–14.5px | 400 | 1.55 (step text is explicit; elsewhere the `styles.css` default of 1.55 applies) |
| Label (subtitle, ingredient quantity, eyebrow captions) | 10.5–14px | 400; eyebrow captions ("Phone · 402pt" style) additionally carry `letter-spacing:.12em` + uppercase | default (not explicit in source) |

**Accepted exception — three weights, not two.** The general guidance is a maximum of two font
weights. This screen carries three (800 inherited for headings, 700 inline override, 400 body),
because that is the source file's own encoding and CONTEXT.md D-06 locks the port "without
design changes." Normalizing to two weights would violate D-06. This is a deliberate, recorded
exception — **not** a defect for an executor to "fix," exactly as with the non-4px spacing
values above.

Base default (from `styles.css`, applies to any net-new text this phase introduces outside the
ported screen): `font-size: 15px; line-height: 1.55; font-weight: 400;` on `--font-body`
(Archivo).

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#fffaf6` | Content-sheet background — the surface almost all recipe content sits on |
| Secondary (30%) | `#fdf1ea` (ingredient cards, timer chips, resting step-number badge) and `#f7e7e0` (tab-track / servings-stepper track) | Card and control-track surfaces |
| Accent (10%) | `{{ accent }}` — default `#e8623c`; the design exposes it as a swappable prop with options `#e8623c` / `#e0452c` / `#d97757` / `#c2543f` | Header/nav strip background · active tab fill · icon strokes (clock / effort / macro icons) · primary "Mark as cooked" CTA fill (uncooked state) · current-step number badge fill |
| Destructive | not applicable | No destructive action exists in Phase 1's UI scope — backend stays thin (D13), no delete/remove affordance is designed or required by APP-01 |

Accent reserved for: the five elements listed above only — never apply it to body text,
dividers, or default icon fills.

**Additional semantic color, outside the 60/30/10 roles:** the favorite/heart indicator uses
its own hardcoded two-tone, independent of the `accent` prop — active `#e0362b`, inactive
`#c9b3aa`. Do not conflate this with `accent`; a change to the accent swatch must not change
favorite-state color.

**Neutral text tokens used throughout:** primary body copy `#2a2320`; secondary/meta text
`#8d7d76`; canvas-only link color `#d85433` / hover `#b9421f` (not used inside the recipe
content itself).

## Open Questions (flagged per CLAUDE.md — mark unverified as UNKNOWN, do not guess)

1. ~~**Recipe-not-found / DB-error handling.**~~ **RESOLVED (owner, 2026-09-06):** an unknown
   recipe id calls Next.js `notFound()`; a failed Drizzle query hits a route-level error
   boundary rendering plain text plus a retry affordance. This is net-new markup, so it uses the
   standard 8pt scale and the base 15px/1.55 Archivo body style — **not** the Recipe Page
   exception values. Error-state *copy* remains UNKNOWN in the Copywriting Contract and is the
   planner's to write.
2. ~~**Favorite (heart) and "Mark as cooked" persistence.**~~ **RESOLVED (owner, 2026-09-06):
   both are ephemeral client-only React state — no backing column, no persistence, resets on
   reload.** A column must NOT be added for either toggle in Phase 1. Original reasoning kept
   below for the record. D-09's schema (`recipes` +
   `ingredients` + `steps`) has no column backing either toggle, and neither is named in
   D-11's reserved-churn table. Recommend treating both as **ephemeral client-only UI state**
   in Phase 1 (resets on reload) unless the planner deliberately adds a column — flagging this
   explicitly so a column doesn't get added silently and spend reserved schema surface D-11
   didn't name.
3. **Subtitle copy references the meal planner.** The source's hardcoded
   `"Wednesday lunch · from this week's plan"` cannot be populated from Phase 1's schema. This
   falls under CONTEXT.md's "Claude's Discretion — exact column types and naming within the
   D-09 recipe core": add a `recipes.subtitle` (or similarly named) text column with a
   Phase-1-appropriate seed value instead of porting the meal-plan-referencing string literally.
4. **Servings base quantity.** The source hardcodes `mult = servings / 2` — i.e., every seed
   ingredient quantity is authored "per 2 servings." The `recipes` table needs a base-servings
   value (either a column, or the seed fixes base servings at 2 and this is documented) so the
   scaler's math derives from real data rather than a literal in ported code.
5. **Responsive breakpoints.** The three frames in `Recipe Page.dc.html` (402pt / 834pt /
   1440px) are Claude Design canvas presentation widths, not CSS breakpoints — no lock exists
   in CONTEXT.md. Default proposed (mark as default, confirm or override before implementation):
   phone layout below 834px, tablet layout 834–1439px, desktop layout at 1440px and above, via
   `min-width` media queries.
6. **Canvas presentation scaffolding vs. shipped UI — do not port the chrome.** The outer flex
   wrapper (`padding:48px 56px 72px; gap:56px`), the per-frame captions ("Phone · 402pt",
   "Tablet · 834pt portrait", "Desktop web · 1440px"), the fixed frame width/height/
   border-radius/box-shadow (the device bezel), and the entire "Notes" sidebar column are
   Claude Design's own canvas annotations — **not** part of the shipped Recipe Page. Only the
   markup inside each frame's content area (nav bar → content sheet → tabs/ingredients/steps/
   CTA) is real UI to port. If in doubt, re-fetch the source design project per IMPORT.md's own
   guidance rather than guessing which parts are chrome.
