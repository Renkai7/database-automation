<objective>
Expand the proven tracer slice horizontally: add the two remaining D-09 tables — `ingredients` and
`steps` — through the same generate/inspect/migrate loop the tracer established, extend the
deterministic seed to the imported design's full recipe content (D-23), and apply the result to the
live development database before anything verifies against it.

This plan carries no tracer task of its own by design: the phase's single `type="tracer"` slice is
plan 01-02 Task 1, and this is one of its expansion tasks (the "real data layer" step). The
architecture it expands from is already proven end to end.

Purpose: D-09 requires three related tables rather than one, because a schema with no relationships
is a weak fixture for a classifier whose whole point is context-awareness. Running the second schema
change through the identical loop is also what proves ENV-02's loop is a loop rather than a one-off.

Output: the complete recipe core in the database, a second journalled migration, and a seed whose
row counts and values Phase 2's restore verification (BKP-04) can assert against.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| schema module → live development database | Everything that changes the database's shape crosses here; a second route across this boundary would be ungated |
| generated migration file → committed history | A hand-edited migration diverges from what the generator would produce and from what any prior environment applied |
| seed script → database rows | The seed deletes before inserting, so a misdirected connection would delete real rows |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-11 | Tampering | schema application path | high | mitigate | The only sanctioned path is generate → inspect → migrate, which leaves an SQL artifact and a journal entry; the direct-sync alternative is a recorded prohibition and is asserted absent by the guardrail suite in plan 01-04 |
| T-01-12 | Tampering | hand-edited migration SQL | medium | mitigate | The migration is regenerated from the schema module rather than edited; the acceptance criteria require the emitted file to be unmodified after generation. **Fixed seed values (deterministic, asserted by later phases):** one recipe, eight ingredients
(Chicken breast 200 g, Basmati rice 90 g, Broccoli 150 g, Spring onions 2, Garlic 2 cloves, Ginger
10 g, Soy sauce 20 ml, Sesame oil 10 ml) and five steps, of which three carry timer labels `12 min`,
`8 min` and `4 min` and two carry none.

## Reserved material this plan deliberately does not build

D-11's reserved-change table exists so Phase 1 does not accidentally spend the change a later phase
needs. None of the following is created here: a `notes` column on `recipes` or a `tags` table
(reserved as Phase 4's SAFE case); a NOT NULL column with a volatile default or a SET NOT NULL on an
existing column (reserved as Phase 4's REVIEW REQUIRED case); a drop of `ingredients` or of any
column the ported screen reads (reserved as Phase 4's BLOCKED case); a rename or restructure of a
column the Recipe Page actively reads (reserved as Phase 7's expand-and-contract case, APP-03, which
needs a column genuinely still in use). D-10 additionally holds back tags, usage counters, meal-plan
days, meal slots and shopping items.
