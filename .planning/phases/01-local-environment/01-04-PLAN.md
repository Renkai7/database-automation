<objective>
Give the developer and Claude Code the two commands Phase 1 exists to hand over: `pnpm db:query`,
a direct connection to the local development database that replaces relaying commands through a
hosting-provider terminal (ENV-05, D-15, D-16, D-17); and `pnpm db:reset`, a single-invocation full
destroy-and-rebuild (ENV-04, D-22, D-24). Then make the phase's structural constraints hold by
mechanical check rather than by anyone remembering them.

This plan carries no tracer task of its own by design: the phase's single `type="tracer"` slice is
plan 01-02 Task 1, and these are its expansion tasks. It shares no files with plan 01-05, but the two
are not run in parallel: Task 2's `db:reset` begins with `docker compose down -v`, which destroys the
container and volume that plan 01-05's build and smoke test read from, so 01-05 declares a dependency
on this plan and runs in the following wave. This plan therefore has the shared local development
database to itself while it is destroying and rebuilding it.

Purpose: CLAUDE.md's first non-negotiable is architectural enforcement over remembered caution. A
query tool that is structurally incapable of reaching another database is that principle in its
concrete form, and a guardrail suite is what keeps it from quietly regressing.

Output: two working root scripts, their coverage, and a guardrail suite that fails when a structural
constraint is broken.
</objective>

    `scripts/db-reset.ts` performs D-22's full teardown in exactly this order, using `execa` so
    argument quoting behaves correctly on Windows, and aborting on the first non-zero exit:

    1. `docker compose down -v` — destroys the container and the named volume. This is deliberately
       slower than dropping and recreating the database inside a surviving container, and that cost is
       accepted: it is the only variant that proves the migration history applies to a truly empty
       instance, which Phase 4's RUN-05 and Phase 2's BKP-03 both depend on.
    2. `docker compose up -d --wait` — blocks until the healthcheck reports healthy and exits non-zero
       on failure. If the installed Compose build does not support the readiness flag, fall back to
       polling `docker compose exec -T db pg_isready -U recipe_app -d recipe_dev` with a bounded
       retry and a clear timeout error, and record in the summary that the fallback was needed.
    3. Open a `pg.Client` and call `assertDevelopmentDatabase` before anything writes. This is the
       structural guard D-24 relies on in place of a prompt.
    4. `drizzle-kit migrate` through the root `db:migrate` target — the full history, not a snapshot.
    5. The deterministic seed through the root `db:seed` target.

    Print a one-line progress marker per step so a failure names the step it happened in. Do not print
    the connection string at any point.

    Per D-24 the script does not prompt and takes no confirmation flag. A prompt that automation
    routinely answers protects nobody, and an unconditional prompt would stop Phase 4's automated
    migration-history tests from reusing this command, which would force a second destructive path to
    exist. Do not import `readline`, `prompts`, `inquirer`, or read `process.stdin`.

    The script takes no arguments and no target parameter; it acts on this workspace's own compose
    project only.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| developer or agent shell → local development database | `db:query` executes arbitrary SQL supplied by the caller; whatever database it reaches gets that SQL |
| command-line arguments and process environment → connection target | Any parameter that influences the target turns a structurally-local tool into a remotely-pointable one |
| `db:reset` → the database's entire contents | The first step of the rebuild destroys a volume unconditionally |
| source files → git remote | Any credential written into a source file leaves the machine permanently |
