<objective>
Make a merge to `main` migrate staging automatically, over a tunnel raised by one named step, with
a credential no unmerged branch can read.

Purpose: `main` is already protected by the Phase 5 ruleset with required checks and an empty
bypass list, so anything reaching it has passed the analyzer, both history axes and both tamper
checks. Triggering on push to `main` therefore adds no second protected branch and no extra merge
step, and the thing gating staging is the gate Phase 5 already proved works. The Environment's
branch restriction — not the Environment itself — is what stops an unmerged branch from adding a
step that reads the staging migration credential, because on a public repository pull requests from
branches do receive repository secrets.

Output: the staging Environment, `.github/workflows/staging-migrate.yml`, and a pipeline record.
</objective>

Create `.github/workflows/staging-migrate.yml`.

Trigger: `on: push: branches: [main]` and nothing else. No `workflow_dispatch` — criterion 4 says
"automatically", which a manual trigger does not satisfy. No `pull_request` and no
`pull_request_target`, matching `pr-gate.yml`'s own recorded rejection of the latter.

Workflow-level `permissions: contents: read` as the baseline, mirroring `pr-gate.yml`. Grant
nothing extra at workflow level.

Workflow-level `concurrency` with a group keyed on the workflow name and the ref, and
`cancel-in-progress: false`. Record in a comment why cancellation is wrong here specifically:
cancelling a job mid-migration would kill the runner process while a statement may be executing,
and the runner's recovery path (`scripts/db-migrate-recover.ts`, `docs/decisions.md` D23) reports
and resolves but never repairs. A second push queues instead.

One job, id and name `staging-migrate`, `runs-on: ubuntu-latest`, `timeout-minutes: 15`
(the WR-01 hang-guard convention every job in this repository follows), `environment: staging`, and
job-level `permissions: contents: read, issues: write` — `issues: write` is needed only by the
tracking-issue step and is scoped at job level exactly as `restore-drill.yml` does it, never at
workflow level.

Steps, each separately named, one logical action per step, following this repository's existing
convention:

1. `actions/checkout@v4` with `ref: ${{ github.sha }}` — this is a push event, so there is no
   `pull_request.head.sha` to reference.
2. `pnpm/action-setup@v4`.
3. `actions/setup-node@v4` with `node-version: 24` and `cache: pnpm`.
4. Install dependencies: `pnpm install --frozen-lockfile`.
5. Confirm the SSH client is present: run `ssh -V`. `06-RESEARCH.md` Assumption A1 records that the
   preinstalled OpenSSH client on `ubuntu-latest` was assumed, not verified; this step is how the
   assumption gets confirmed on the first real run, mirroring `pr-gate.yml`'s own `gh --version`
   step. Add a comment saying that if this step ever fails, the fix is an explicit
   `apt-get install -y openssh-client` step, not removing the check.
6. "Establish the private tunnel to staging Postgres — the ONLY SSH-aware step (D-02)". It writes
   `STAGING_SSH_PRIVATE_KEY` to a file under `~/.ssh` with mode 600, writes
   `STAGING_SSH_KNOWN_HOSTS` to `~/.ssh/known_hosts`, and starts a background
   `ssh -N -L 15432:${{ secrets.STAGING_TUNNEL_DESTINATION }} -i <keyfile>
   -o ExitOnForwardFailure=yes -o StrictHostKeyChecking=yes
   ${{ secrets.STAGING_SSH_USER }}@${{ secrets.STAGING_SSH_HOST }}`, recording its PID into
   `$GITHUB_ENV`. Use `ExitOnForwardFailure=yes` so a `permitopen` refusal makes ssh itself exit
   non-zero rather than leaving an unusable tunnel — hard-fail, never warn (`01-CONTEXT.md` D-20).
   Use `StrictHostKeyChecking=yes` against the pinned known-hosts value; never
   `StrictHostKeyChecking=no`, which silently accepts any host key and defeats host verification.
   Add a comment naming this as the single step D-02's seam permits to know the mechanism, and
   stating that a later swap to WireGuard replaces this step alone.
7. "Wait for the forwarded port": `pnpm exec tsx scripts/ci/wait-for-staging-port.ts`. Invoke with
   `pnpm exec`, not `pnpm run` — `05-03`'s recorded live finding is that `pnpm run`'s stdout banner
   corrupted a script's output. Comment that this step is what makes the previous step's contract
   ("after me, the staging URL connects") true, and that without it the migration's first
   connection attempt would race the tunnel's startup.
8. "Run the staging migration — no step after this references SSH": `pnpm db:migrate:staging`, with
   `env: RECIPE_STAGING_MIGRATOR_DATABASE_URL: ${{ secrets.RECIPE_STAGING_MIGRATOR_DATABASE_URL }}`.
   Do NOT assemble the connection string from parts in this file: supply it whole from the
   Environment secret. Comment that this is deliberate for two reasons — it keeps any PostgreSQL
   connection-string prefix out of `.github/`, which this repository's guardrail suite bans across
   the source surface, and it keeps the workflow ignorant of the database name and the local port.
9. "Tear down the tunnel" with `if: always()`, killing the recorded PID and tolerating an
   already-dead process.
10. "Open or update the tracking issue on failure" with `if: failure()`, copied from
    `restore-drill.yml` lines 84-98 near-verbatim: `set -euo pipefail`, a fixed title, a body
    carrying the run URL built from `GITHUB_SERVER_URL`/`GITHUB_REPOSITORY`/`GITHUB_RUN_ID`, a
    `gh issue list --search "\"<title>\" in:title" --state open` lookup, and `gh issue comment` when
    one exists or `gh issue create` when none does. Comment that this exists because a push-triggered
    workflow has no pull request to comment on — the same problem `restore-drill.yml` already
    solved — and that the schema is deliberately left as the runner left it, with no automatic
    rollback and no pre-migration snapshot (`PROJECT.md` Out of Scope; `docs/decisions.md` D23).

Add no new required status check and change no existing check name: Phase 5's required-check names
are ruleset configuration and must stay stable. Note that in a header comment.

## Trust Boundaries

| Boundary | Description |
