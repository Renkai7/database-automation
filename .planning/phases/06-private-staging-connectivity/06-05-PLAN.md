<objective>
Give staging its own pinned entry point over the identical migration runner core, and the one
mechanism-aware helper the connectivity step needs — without letting either learn what the
connectivity mechanism is.

Purpose: `01-CONTEXT.md` D-16 and `02-CONTEXT.md` D-06's "no command accepts a target" rule stays
literally true only if each command has exactly one possible destination fixed in source. A
`--env staging` flag would reintroduce a command that accepts a target in spirit, and inferring the
environment from whichever variable happens to be present would make the destination a property of
ambient environment rather than of the command. A separate thin sibling costs roughly forty lines
of deliberately divergent wiring and buys both.

Output: `scripts/db-migrate-staging.ts`, the dynamic half of the staging pin, and an argument-free
wait-for-port helper.
</objective>

  <action>
Create `scripts/ci/wait-for-staging-port.ts`. It polls a TCP endpoint until it accepts a connection
or a bounded deadline passes.

The research sketch for this helper takes host and port from `process.argv`. Do not do that: every
module under `scripts/ci/` is covered by this repository's unconditional no-argument ban, derived
at test time from `git ls-files scripts/ci`, and a command that accepts an argument is the command
that later accepts a target. Pin them instead as source constants —
`const LOCAL_FORWARD_HOST = "127.0.0.1";` and `const LOCAL_FORWARD_PORT = 15432;` — with a comment
stating that this local port must match the workflow's own forward, that both belong to the
connectivity step and to nothing downstream of it (D-02), and that changing either is a
safety-relevant source diff.

Implementation: a `tryConnect` returning a promise that resolves true on `connect` and false on
`error`, always ending the socket; a loop with a `DEADLINE_MS = 30000` budget and a 500 ms sleep
between attempts; a final throw naming the host, the port and the elapsed budget when the deadline
passes. Never `process.exit` — set `process.exitCode` once, in a `.catch` at module scope, rendering
the error with `safeErrorMessage`. Print one line on success reporting how long it waited, so a
workflow log shows whether the tunnel came up promptly or barely.

Add a header comment recording the discretionary decisions this file settles: the CI tunnel
lifecycle is inline workflow steps rather than a composite action (one fewer indirection for a
single consumer); the wait is a bounded poll rather than a fixed sleep, because a fixed sleep is
exactly the "remembered timing" this project's non-negotiables reject; and if the tunnel dies after
this helper succeeds, nothing here detects it — the migration's own connection error is what
surfaces it, and that is deliberate, because a watchdog here would be a second mechanism-aware
component downstream of the connectivity step.

Do not add a `pnpm` script for this helper: it is invoked by the workflow as
`pnpm exec tsx scripts/ci/wait-for-staging-port.ts`, matching how `scripts/ci/analyze-gate.ts` is
invoked (`05-03`'s recorded finding that `pnpm run`'s stdout banner corrupted a script's output).
