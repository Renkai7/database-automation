<objective>
Close the loopback collision the tunnel created: make the development guard require a server-side
environment marker, fail closed when it is absent or unreadable, and prove the refusal against a
real PostgreSQL rather than against a mock.

Purpose: `ssh -L` makes a remote staging database appear at `127.0.0.1:5432`.
`assertLocalDevelopmentTarget` requires loopback, port 5432 and database `recipe_dev` — so with a
tunnel open, two of its three checks already match staging, and only the database *name* stands
between a schema-sync command and the staging schema. If staging were ever named `recipe_dev` —
plausible, since that name would come from copying the compose file — the development pin passes.
Naming staging `recipe_staging` and forwarding to a port other than 5432 are conventions someone
must remember, which is the shape `CLAUDE.md`'s first non-negotiable rejects. A fact the server
itself reports is not.

Output: the marker read/seed pair in `scripts/env.ts`, the fail-closed extension of
`assertDevelopmentDatabase`, a Testcontainers refusal proof, and the tightened staging probe. This
is D-08's automated half; its performed half is plan 06-06.
</objective>

`ENVIRONMENT_MARKER_PREFIX = "gsd-environment="`,
`DEVELOPMENT_ENVIRONMENT_MARKER = "gsd-environment=development"`,
`STAGING_ENVIRONMENT_MARKER = "gsd-environment=staging"`.

Add `export async function readEnvironmentMarker(client: QueryableClient): Promise<string | null>`.
It issues exactly one query: select `shobj_description(oid, 'pg_database')` aliased as `name` from
`pg_database` where `datname = current_database()`. Return `rows[0]?.name ?? null`. Do not catch
anything — a read that errors must propagate, because an unreadable marker is a refusal, not a
pass. Document in a comment why a database-level `COMMENT` was chosen over the two alternatives
`06-CONTEXT.md` left to discretion: a marker table row travels inside a `pg_dump` payload (the
exact objection `docs/decisions.md` D21 records against a stored row), and a custom GUC set with
`ALTER DATABASE … SET` only takes effect in subsequent sessions, so an ensure-then-read in one
session cannot see its own write. A database comment has neither problem, is readable by an
unprivileged role, and cannot be set by a connecting session the way a session GUC can.

Add `export async function ensureDevelopmentMarker(client: QueryableClient): Promise<void>`. It
issues one anonymous `DO` block that executes
`format('COMMENT ON DATABASE %I IS %L', current_database(), <the development marker constant>)`.
Use `format` with `%I`/`%L`; do not concatenate the database name into SQL text. This function is
self-healing by design so that a `pnpm db:reset` needs no manual follow-up step, and its comment
must say so.

Extend `assertDevelopmentDatabase` so its body runs in exactly this order, and record the ordering
rationale in a comment because the ordering *is* the guard:
first, the existing `SELECT current_database() AS name` check against `expectedName`, throwing
unchanged on mismatch — this must stay first so the seeding step below can never run against a
database that is not the pinned development database;
second, `readEnvironmentMarker`;
third, if and only if the marker is null, call `ensureDevelopmentMarker` and re-read;
fourth, throw unless the marker equals `DEVELOPMENT_ENVIRONMENT_MARKER`. The thrown message must
say that the connected server does not report itself as the development environment, name the
expected marker value, and name neither the observed marker value nor anything from the connection
string. Add no option, parameter or environment variable that skips any of this.

In `scripts/env.test.ts`, extend `stubClient` so it answers both statement shapes: the
`current_database()` select and the `shobj_description` select, with the marker value supplied per
test (including a `null` case and a throwing case), and so it records which statements were issued
in order. Keep the three existing cases passing and add one test per `<behavior>` bullet above.
The ordering bullet is asserted on the recorded statement sequence, not merely on the thrown error.

Write the new tests RED first and confirm they fail for the stated reason before implementing.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `127.0.0.1:5432` as seen by a development command | Under an SSH forward this address is no longer necessarily the local container. |
| A connecting session -> the environment fact it claims | The session must not be able to author the fact it is checked against. |
| `apps/recipe-app/drizzle.config.ts` -> whatever database it resolves | Synchronous, pre-connection; cannot await a server round trip. |
