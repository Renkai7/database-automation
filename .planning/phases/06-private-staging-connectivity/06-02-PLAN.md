<objective>
Create the three staging database roles from a committed, idempotent SQL script, prove every
privilege claim against a real PostgreSQL 17 rather than asserting it in prose, run the script
once against real staging, and repoint the deployed application off the Coolify-generated owner
credential.

Purpose: criterion 4 requires the migration credential to be different from — and more restricted
than — the application's runtime credential. That is only a real claim if it is a database-enforced
privilege boundary, not a naming convention. `06-CONTEXT.md` D-09 fixes the reading being verified:
neither role is the superuser Coolify generates, the migrator's reach stops at one database, and
the application's stops at the data.

Output: `scripts/sql/bootstrap-roles.sql` (which Phase 7 reruns against production unchanged), an
argument-free runner, a Testcontainers proof of every privilege claim, and a performed record.

Sizing note: this plan carries four tasks, one of which is a checkpoint that produces no
implementation context. The implementation load is three tasks.
</objective>

Create `scripts/sql/bootstrap-roles.sql`. It must be environment-agnostic so Phase 7 reruns it
against production unchanged: it names no database, and every value that differs per environment
arrives as a session GUC the runner sets. It reads exactly four settings via `current_setting`:
`gsd_bootstrap.migrator_password`, `gsd_bootstrap.readonly_password`,
`gsd_bootstrap.app_password`, and `gsd_bootstrap.environment_marker`.

Contents, in order:

1. A `DO` block that, for each of `recipe_migrator`, `recipe_readonly` and `recipe_app`, checks
   `pg_roles` for the name and either `EXECUTE format('CREATE ROLE %I WITH LOGIN PASSWORD %L ...',
   ...)` or `EXECUTE format('ALTER ROLE %I WITH LOGIN PASSWORD %L ...', ...)`. `CREATE ROLE` has no
   `IF NOT EXISTS` clause in PostgreSQL 17, so the `pg_roles` check is the idempotency mechanism —
   never `DROP ROLE` then recreate, which would revoke every grant made since the last run and
   orphan owned objects. Attributes: `recipe_migrator` gets `NOSUPERUSER NOCREATEDB NOCREATEROLE
   NOINHERIT CONNECTION LIMIT 5`; `recipe_readonly` gets `NOSUPERUSER NOCREATEDB NOCREATEROLE
   CONNECTION LIMIT 5`; `recipe_app` gets `NOSUPERUSER NOCREATEDB NOCREATEROLE CONNECTION LIMIT 20`.
   Use `format` with `%I` for identifiers and `%L` for the password, never string concatenation.
2. A `DO` block granting `CONNECT` on `current_database()` to all three roles, via
   `EXECUTE format('GRANT CONNECT ON DATABASE %I TO recipe_migrator, recipe_readonly, recipe_app',
   current_database())`, and granting `CREATE` on the database to `recipe_migrator` only — the
   migrator needs it to create the `runner` and `drizzle` schemas the runner bootstraps
   imperatively (`04-CONTEXT.md` D-22).
3. `ALTER SCHEMA public OWNER TO recipe_migrator;` — the migrator owns the schema going forward,
   which is what makes the `ALTER DEFAULT PRIVILEGES FOR ROLE recipe_migrator` clauses below apply
   to everything a future migration creates.
4. `GRANT USAGE ON SCHEMA public TO recipe_app, recipe_readonly;`
5. Present-tense grants for what already exists — omitting these is the correctness gap
   `06-RESEARCH.md` Pitfall 4 names: `GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA
   public TO recipe_app;`, `GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO recipe_app;`,
   `GRANT SELECT ON ALL TABLES IN SCHEMA public TO recipe_readonly;`.
6. Future-tense grants for what migrations will create: `ALTER DEFAULT PRIVILEGES FOR ROLE
   recipe_migrator IN SCHEMA public GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO recipe_app;`,
   the matching `GRANT USAGE, SELECT ON SEQUENCES TO recipe_app;`, and `GRANT SELECT ON TABLES TO
   recipe_readonly;`.
7. `REVOKE CREATE ON SCHEMA public FROM recipe_app, recipe_readonly;` — belt and braces, and it
   makes the intent readable in the file itself.
8. A `DO` block seeding the database-level environment marker:
   `EXECUTE format('COMMENT ON DATABASE %I IS %L', current_database(),
   current_setting('gsd_bootstrap.environment_marker'))`. A database comment was chosen over a
   marker table deliberately: `scripts/env.ts`'s D-21 comment rejects a stored row because a row
   travels inside a `pg_dump` payload and would survive a restore into a differently-named
   database; a database-level comment is a property of the database object and is not emitted by a
   plain `pg_dump`. Put that reasoning in a comment at the top of the block. If PostgreSQL refuses
   `COMMENT ON DATABASE` inside the runner's transaction, move this one statement to a separate
   statement the runner issues after `COMMIT` — do not silently drop it, and record the deviation.

Create `scripts/bootstrap-roles.ts`. Header comment, following `scripts/db-migrate.ts`'s
convention: this is the *staging* bootstrap; it accepts no argument, no flag and no ambient-variable
inference; it is run by hand, once, with the Coolify-issued credential; it is deliberately NOT a

Promise<number>` that reads `getStagingBootstrapUrl()`, opens one `pg` `Client`, and — before any
DDL — asserts the connected server reports `current_database()` equal to
`EXPECTED_STAGING_DATABASE_NAME`, refusing otherwise. Then, in this order: issue three
`SELECT set_config($1, $2, false)` calls passing each password as a bound parameter (never
interpolated into SQL text), a fourth setting `gsd_bootstrap.environment_marker` to the source
constant `"gsd-environment=staging"`, then `BEGIN`, then the whole contents of

Print only step names and, at the end, the result of a verification query listing
`rolname, rolsuper, rolcreatedb, rolcreaterole, rolconnlimit` from `pg_roles` for the three roles.
Never print a password, a URL, a host or a port. Use `safeErrorMessage` for every error render and
the `run().then(code => { process.exitCode = code; }).catch(...)` tail — never a synchronous
`process.exit`. Do not write a literal PostgreSQL connection-string scheme prefix into this file.

In `scripts/env.ts` add, following the `getBackupDestination` opt-in precedent (NOT `EnvSchema` —
