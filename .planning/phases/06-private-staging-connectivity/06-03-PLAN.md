<objective>
Establish, from three independent vantages, that reaching staging over the private path opened no
inbound database port — and write it down in a form that can be re-run and compared later.

Purpose: `PITFALLS.md` line 535, cited by `06-CONTEXT.md`'s own canonical refs, is that "reachable"
is not "safely scoped". Each vantage answers a different question: a Hetzner firewall can hide a
live listener, and a listener can sit behind a closed firewall that one rule change would expose.
None of the three alone is sufficient, which is why criterion 2 is proven by a record covering all
three rather than by a single check.

Output: `docs/51-staging-port-proof.md`, following `05-CONTEXT.md` D-18's performed-record
precedent.
</objective>

  <instructions>
Three independently-performed observations of whether a PostgreSQL port is reachable from outside
the Hetzner host. The executor has no off-host vantage, no shell on the host, and no Coolify UI
access, so all three must come from the owner.

Do NOT open the port "temporarily to check" — `PITFALLS.md` line 550 is explicit about this, and a
proof that required exposing the thing it is proving is not a proof.

Perform all three and paste the raw output of each, with the date and the exact command used.

**Vantage 1 — off-host, what an attacker sees.** From the Windows development machine, with the
SSH tunnel CLOSED, run PowerShell's `Test-NetConnection -ComputerName <hetzner-public-address>
-Port 5432` and paste the whole result including `TcpTestSucceeded`. Repeat for any other port the
recon in `docs/50-staging-connectivity-recon.md` flagged as possibly database-related. If you have
`nmap` installed and prefer it, use it and say so — either tool answers the same question, and
`Test-NetConnection` needs no install.

**Vantage 2 — host-side, what is actually bound.** In an SSH session on the Hetzner host, run
`ss -tlnp` and paste the complete output. Do not filter it — the point is to see everything
listening, not only what you expected to find.

**Vantage 3 — the platform's own claim.** In the Coolify UI, for `recipe_staging` and for every
other database resource on this instance, report the state of the "Publicly Accessible" toggle and
the exact label the UI shows next to it. If any database anywhere on this instance has it ON, say
so — that is a finding to record, not a reason to stop.

Then, separately: attempt an interactive login with the owner's restricted staging key
(`ssh staging-db` with no `-N`) and paste what happens, and attempt a second forward the
`permitopen` line does not allow (for example `ssh -N -L 15433:127.0.0.1:22 staging-db` followed by
a connection attempt to 127.0.0.1:15433) and paste what happens. These two prove the key's scope
rather than assuming `restrict`/`permitopen` behave as documented.

Redact the Hetzner public address to `<host>` in everything you paste — this repository is public.
If you could not perform a vantage, say which and why; do not substitute a guess.
