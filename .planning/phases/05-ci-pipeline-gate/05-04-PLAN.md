<objective>
Build the two mechanical checks that catch a hand-edited migration and an edit to a migration a
previous merge already applied — without relying on a reviewer noticing.

Purpose: CI-05, via D-09 and D-10. The grounding fact established during discussion is that
`apps/recipe-app/drizzle/meta/_journal.json` carries **no content hash** — only `idx`, `version`,
`when`, `tag`, `breakpoints`; the sha256 lives solely in the `drizzle.__drizzle_migrations` table,
which this phase has no shared database to read. Git and `schema.ts` are therefore the only
available references, and every tamper design that assumed a hash is wrong.

Output: two `scripts/ci` checks with synthetic-fixture tests, ready for plan `05-06` to wire into
the `tamper-checks` job.
</objective>

    - Head journal where idx 2's `when` changed: throws, message names idx 2.

      unchanged: passes — order in the array is not the identity, `idx` is.
    - Head journal that renumbers an existing entry's `idx` (closing the "renumber so a modified
      migration re-runs as new" dodge): throws.

      could not be parsed — never silently treated as "no entries".

  <action>
    Extend `scripts/ci/check-append-only.ts` with
    `assertJournalEntriesAppendOnly(baseJournalText: string, headJournalText: string): void`.

    Parse both texts. A parse failure on either side throws with a message naming which side
    failed — an unparseable base journal must never be treated as an empty entry list, because
    that would make every existing entry vacuously unchanged and turn the check into a no-op.

    Index the base entries by `idx`. For each base entry, find the head entry with the same `idx`;
    throw if it is absent, naming the `idx` and the base `tag`. Throw if the head entry's `tag` or
    `when` differs from the base entry's, naming the `idx` and which field changed. Do not compare
    array position — reordering is not tampering, and `idx` is the identity. Do not reject new
    entries with a higher `idx` — appending is the normal case that every new migration performs.
    Also throw when the same `idx` appears twice in the head journal, mirroring the
    "ordering must be total" integrity error the adapter already raises.

    Wire it into the `import.meta.main` entry point: obtain the base journal with
    `git show <base>:apps/recipe-app/drizzle/meta/_journal.json` and the head journal with
    `git show <head>:...` — read both from git object storage, not from the working tree, so the
    check is not influenced by anything the job did to the checkout. If `git show` fails for the
    base because the file did not exist at the base commit, treat that as "no prior journal" only
    when git's own error identifies a missing path, and say so in the log; any other failure
    throws.

    Extend `tests/ci/check-append-only.test.ts` with the behavior rows above, all synthetic JSON
    strings.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| pull-request branch → tamper checks | The author controls both the migration files and the journal being compared. |
| git object storage → check input | The base journal is read from git, not from the working tree the job may have modified. |
| working tree → drift signal | Generation writes into the same directory the check inspects. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-19 | Tampering | editing a migration a previous merge already applied | critical | mitigate | `assertMigrationFilesAppendOnly` refuses any non-added path under the migrations directory, with git as the reference and no exemption list. |
| T-05-20 | Tampering | renumbering or deleting a journal entry so a modified migration re-runs as new | high | mitigate | `assertJournalEntriesAppendOnly` keys on `idx` and compares `tag` and `when`; a disappearing entry and a duplicated `idx` both throw. |
| T-05-21 | Tampering | a shallow clone producing an empty diff that looks like a clean pull request | critical | mitigate | Both SHAs are resolved with `git cat-file` before diffing; an unresolvable SHA throws and names `fetch-depth`. Plan `05-06` sets `fetch-depth: 0` on the job. |
| T-05-22 | Tampering | an unparseable base journal read as "no prior entries", making the comparison vacuous | high | mitigate | A parse failure on either side throws and names which side failed. |
| T-05-23 | Spoofing | a dirty working tree misread as "no drift", or generated output misread as a pre-existing edit | high | mitigate | `assertWorkingTreeClean` runs before generation and refuses a non-empty porcelain result. |
| T-05-24 | Repudiation | relying on a generation exit code whose drift-found behaviour was never observed | medium | mitigate | The exit code is logged as an observation and never used as the signal; assumption A4 stays UNKNOWN in the record. |
| T-05-25 | Tampering | a detector proven by mutating real shipped migration data | medium | mitigate | Every test drives synthetic in-memory fixtures, following the repository's own WR-04 precedent; the real falsification is performed once, observably, in plan `05-08`. |
</threat_model>
