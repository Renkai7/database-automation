      publication record is appended to this same file so the diligence and the act live together.

      implemented, and the "the owner's plan tier stays UNKNOWN" constraint.

  </read_first>
  <files>docs/40-public-release-audit.md</files>
  <action>
    First, prove the tooling exists rather than assuming it: run `gh --version` and
    `gh auth status`, and record both outputs. If either fails, stop and surface the user_setup
    step rather than working around it.

    Create the repository with `gh repo create <name> --<visibility-from-task-1> --source=. --remote=origin --push`,
    where `<name>` is `database-automation` unless the owner named a different one at the Task 2
    checkpoint. Use the flags exactly: `--source=.` makes the current directory the source,
    `--remote=origin` names the remote, `--push` performs the initial push of the current branch.

    Then read back — never trust the flags that were passed:
    - `gh repo view --json visibility,defaultBranchRef,url` — the observed visibility, default
      branch, and URL.
    - `git rev-list --count HEAD` locally and `git rev-list --count origin/main` after a
      `git fetch origin` — these two numbers must be equal. If they differ, the push was partial
      or shallow and this task fails.
    - `git rev-parse HEAD` and `git rev-parse origin/main` — these must be equal.
    - `gh api repos/{owner}/{repo}/actions/permissions/workflow` — the default workflow permission
      level. Record the observed value verbatim. If it reports `read`, set it to `write` with
      `gh api --method PUT repos/{owner}/{repo}/actions/permissions/workflow -f default_workflow_permissions=write`
      and read it back again; a read-only default token would make D-16's sticky comment fail on
      the first real pull request and would be diagnosed as a comment bug rather than a
      repository setting.

    Append a `## Publication record` section to `docs/40-public-release-audit.md` carrying: the
    date, the repository URL, the observed visibility, the observed local and remote commit
    counts, the observed HEAD SHAs, the observed-before and observed-after Actions default
    workflow permission values, and the `gh --version` output. Every value is written as observed,
    with the command that produced it quoted — the same discipline `docs/20-restore-runbook.md`
    and `docs/30-migration-runner.md` already follow.

    Also record, under a `### Still UNKNOWN` subheading, the two things this task does **not**
    settle: the owner's GitHub plan tier (public visibility is what makes it not matter), and
    whether `administration: write` on a workflow `GITHUB_TOKEN` is sufficient to see a ruleset's
    `bypass_actors` (settled in plan `05-08`, not here).

    Commit the record locally. Note for the executor: a direct push to `main` is still permitted
    at this point — the ruleset does not exist until plan `05-08` — but from `05-03` onward this
    phase's own work travels through pull requests, so prefer a branch even now.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| local repository → github.com | Every commit crosses at once; the boundary is one-way. |
| developer workstation → GitHub credential store | `gh auth login` holds a token that can create repositories and, later, rulesets. |
| GitHub API response → this repository's record | The record must reflect what the API said, not what was requested. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-06 | Information Disclosure | the push itself | critical | mitigate | Gated behind plan `05-01`'s completed audit and its blocking human disposition; Task 2's checkpoint restates the live commit count and finding count before the act. |
| T-05-07 | Spoofing | trusting `--public` rather than the observed visibility | medium | mitigate | Visibility is read back with `gh repo view --json visibility` and recorded as observed; the acceptance criterion tests the read-back value, not the flag. |
| T-05-08 | Tampering | a partial or shallow push mistaken for a full publication | high | mitigate | Local and remote commit counts and HEAD SHAs are compared; unequal values fail the task. |
| T-05-09 | Elevation of Privilege | a workflow `GITHUB_TOKEN` with a read-only default, silently breaking D-16 | medium | mitigate | The default workflow permission is read back and set to `write` explicitly; the acceptance criterion asserts the read-back value. |
| T-05-10 | Information Disclosure | a personal access token written into a tracked file | high | mitigate | `user_setup` states plainly that `gh auth login` stores the credential in the OS keychain and that no token is written to `.env` or any tracked file; the repository's existing guardrail suite already fails on a committed connection string. |
| T-05-11 | Repudiation | the owner's GitHub plan tier assumed rather than known | low | accept | Recorded as UNKNOWN in the publication record. D-02's public visibility is precisely the design that makes the unknown not load-bearing. |
