<objective>
**TRACER.** Take this repository from "a remote exists" to "a real pull request whose `analyze`
check ran the real analyzer over the real committed migration history and wrote its complete
verdict onto the pull request itself" — one path, wired end to end, through every layer this phase
will later expand.

Purpose: this is the thinnest thing that proves the whole chain. It touches the pure renderer in
`packages/automation`, the thin `gh` adapter in `scripts/ci`, the workflow file, GitHub's own
check reporting and GitHub's own comment API. If any of those five layers cannot be wired the way
this phase assumes, that is discovered here — after one plan — rather than after five.

This is production-quality, not a prototype. The `analyze` job built here is one of the six
required checks the ruleset will name in plan `05-08`; nothing about it is thrown away.

Output: a working `analyze` job, a tested pure renderer exported from the package barrel, and a
real pull request that demonstrably carried the verdict.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| pull-request branch content → CI job | Migration SQL, file paths and branch names are author-controlled and cross into a job holding a write-capable token. |
| CI job → public pull-request comment | Rendered markdown is published where anyone can read it. |
| analyzer process → job exit code | The check's pass/fail is derived from another process's exit code. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
