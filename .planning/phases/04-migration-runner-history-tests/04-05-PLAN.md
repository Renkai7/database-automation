<objective>
Close the one window this system's design leaves open. For a wrapped file, execution and
recording are already atomic (D-12). For an unwrapped file there is no transaction to make them
atomic, so the runner writes an in-flight marker before the statement runs and resolves it once
the ledger row lands — and any later run that finds an unresolved marker refuses everything and
says exactly which migration and which statement was mid-flight. Recovery is
`pnpm db:migrate:recover`: it reports, including every INVALID index it finds, and resolves the
marker. It never touches `_journal.json` and it never repairs the schema itself.

Purpose: RUN-08, and criterion 4. Because plan 04-04 refuses mixed files, the only residual
partial state in the whole system is a failed `CREATE INDEX CONCURRENTLY` leaving an INVALID
index — this plan handles exactly that case, deliberately, rather than discovering it later.
Output: the marker lifecycle in the runner-owned table, the recovery command, and an automated
proof of the whole cycle against a real database.
</objective>

## Trust Boundaries

| Boundary | Description |
