<objective>
Make `pnpm db:migrate` the runner, end to end, against the real pinned development database:
read each committed migration's bytes once, classify **those exact bytes** in-process, refuse
BLOCKED with no override, split by AST-reported statement boundaries, execute wrapped under
connect-time `lock_timeout`/`statement_timeout` that the runner verifies actually took effect,
and write both a byte-compatible `drizzle.__drizzle_migrations` row and a complete run-report
row in a runner-owned table. Then close the second door: drizzle-kit's own `migrate`
sub-command becomes structurally unreachable from anywhere in this repository.

Purpose: this is D12 — the one enforcement point that cannot be bypassed from inside the
system (D-01, D-02, D-03, D-04, D-12, D-13, D-14, D-15, D-19, D-27, D-28). Every later plan in
this phase expands out from the path this plan proves.
Output: the runner core in `packages/automation/src/runner/`, the pinned thin entry point
`scripts/db-migrate.ts`, the `db:migrate` script swap, and the structural assertion that no
second migrate path exists.
</objective>

`RUNNER_CONNECTION_OPTIONS` built from them as the libpq startup-options string
`-c lock_timeout=3000 -c statement_timeout=30000` (build it by interpolating the two constants,

`assertTimeoutsInEffect(client: RunnerClient): Promise<void>` which runs
`SELECT name, setting FROM pg_settings WHERE name IN ('lock_timeout','statement_timeout')` and

concurrent-index exemption.

**`packages/automation/src/runner/run-migrations.ts`** — the orchestrator. Export
`runMigrations(client: RunnerClient, options: RunMigrationsOptions): Promise<RunReport>` where
options carry `migrations: MigrationFile[]`, `rules: RulesFile`, and an injectable
`now?: () => Date`. There is deliberately **no** parameter, flag, or environment read capable of
weakening a verdict. Per migration, in ascending `idx` order:
1. skip when `lastAppliedMillis >= file.when` (drizzle's own comparison, from `ledger.ts`);
2. call `analyzeSql(file.sql, rules)` on the exact string already in memory — never re-read the
   path;
3. if the result verdict is `BLOCKED`, record a `refused` run entry with the complete findings,
   throw `MigrationRefusedError` carrying `RUNNER_EXIT_CODES.REFUSED_BLOCKED`, and apply nothing
   further — the whole run stops (D-02, D-08's ordering rationale);
4. let an `AnalyzerParseError` propagate as `MigrationRefusedError` carrying
   `REFUSED_PARSE_FAILURE`, applying nothing at all — no verdict can never mean proceed (D-08);
5. if the verdict is `REVIEW_REQUIRED`, print every rule id and every rationale from every
   finding before executing — the complete findings list, never a summary (D-05, D-06) — and
   proceed;
6. `await splitStatements(file.sql)`, then call
   `decideTransactionPolicy(result.findings)` from `./transaction-policy` — for this task that
   module does not exist yet, so inline the decision as a single named local function
   `decideTransactionPolicy` in this file returning `{ wrap: true }` unconditionally, with a
   comment stating plan 04-04 replaces it with the real fact-driven module once the
   `transactionHostile` fact exists. The call site must already be shaped so that swap is a
   body change, not a restructure;
7. wrapped path: `client.query("BEGIN")`, one `client.query(stmt.text)` per split statement
   (never one call for the whole file — Pitfall 1: a multi-statement simple query is implicitly
   one transaction), then `insertLedgerRow` in the same transaction (D-12), then
   `client.query("COMMIT")`. On any error, `client.query("ROLLBACK")`, record a `failed` run
   entry carrying the failing statement index and `safeErrorMessage(error)`, and throw
   `MigrationRefusedError` carrying `EXECUTION_FAILED`;
8. record an `applied` run entry with the complete `findings` array, `statement_count`,
   `wrapped`, `duration_ms`, and `rules_version`.
Return a `RunReport` carrying `runId`, the ordered `entries: RunReportEntry[]` (one per
migration considered, including skipped ones), and the worst verdict seen. Every `console`
call in this module goes through `safeErrorMessage` for error values.
