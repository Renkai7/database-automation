database (data dump + globals dump + manifest), start a genuinely fresh disposable
PostgreSQL 17 container, restore both dumps into it, and assert real restored content

and names the failing step when any part of the chain breaks.

## Decisions this plan implements

| Decision | Rating | Note |
|---|---|---|
| D-01 `-Fc` custom-format data dump | reversible | Format choice behind `runBackup`; swapping it touches one call site and the restore flags. |
| D-02 separate `pg_dumpall --globals-only` artifact | reversible | An additional file at the destination. |
| D-03 destination outside the repository | costly | Referenced by the backup tool, the restore tool, the drill harness, the status record and the runbook. Changing its shape later means changing all of them. Flagged, not gated. |
| D-04 destination not repo-relative | costly | Same surface as D-03. |
| D-05 JSON manifest recorded at backup time | reversible | Schema is versioned in one module; adding fields is additive. |
| D-06 no command accepts a target | **one-way** | Recorded on Task 1 as `<reversibility rating="one-way">`. **No `checkpoint:decision` is inserted**: `02-CONTEXT.md` records the owner making exactly this choice with the alternative (`db:restore --target <url>`) named and rejected — the door is already walked through, and re-asking it would be the "gating a decision already made" anti-pattern. |
| D-11 `@testcontainers/postgresql` for the drill target | reversible | Harness lifecycle behind `runDrill`. |
| D-12 `postgres:17` (glibc) for every server, `postgres:17-alpine` only for client tooling | reversible | Pinned as a named constant. This plan runs client binaries inside whichever `postgres:17` server container already bundles them (RESEARCH Open Question #1), so no alpine client container is started — the recommendation's actual concern (never run the *server* on alpine) is satisfied by construction. |

## Claude's-discretion choices made here (recorded, per D-03/D-04 discretion items)

- **Destination mechanism:** a new environment variable `RECIPE_BACKUP_DESTINATION`, validated
  by `scripts/env.ts` — the project already has exactly one configuration mechanism and adding a
  second for one value adds discovery cost with no benefit (RESEARCH Open Question #2).
  It is **not** added to the module-level `EnvSchema`: doing so would hard-fail the Next.js app,
  `drizzle.config.ts` and the seed for anyone who never takes a backup.
- **Retention:** artifacts accumulate under timestamped filenames; nothing is overwritten and
  nothing is pruned automatically. Pruning is storage-lifecycle policy and belongs with the
  deferred off-server-storage work, not here. `readLatestManifest` picks the newest by
  lexicographic filename order, which the compact-timestamp format makes chronological.

**Manifest module (`scripts/backup-manifest.ts`).** A standalone module with no
module-load side effects, importable from a test without opening a database connection —
the same property `scripts/verify-migration-state.ts` deliberately has. Export:
`compactTimestamp(date)` returning a `YYYYMMDDTHHMMSSZ` string containing no colon and no
other character from the Windows-reserved set (a raw ISO-8601 string used in a filename does
not throw on Windows — it silently writes the content into a hidden alternate data stream, so
this helper is load-bearing, not cosmetic); `sha256File(path)` hashing a file's bytes with
`node:crypto`; a zod `ManifestSchema` and its inferred `BackupManifest` type; `writeManifest`
and `readManifest` that both `.parse()` through the schema, so a hand-edited or truncated
manifest fails loudly on read rather than being silently trusted; and
`readLatestManifest(destination)` returning the newest manifest by lexicographic filename
order. Manifest fields for this task: `takenAt` (ISO-8601 UTC string — a JSON *value*, where a
colon is safe), `postgresVersion`, `gitCommit`, `appliedMigrationCount`, `dataDump` and
`globalsDump` each `{ file, sha256 }`, and `rowCounts` keyed by qualified table name. The
schema must have **no field capable of holding a connection string, a role name's password, or
a password hash** — that is D-05's "no credentials" clause expressed as a type, not a habit.

**Backup (`scripts/backup.ts`).** Export `runBackup(): Promise<BackupManifest>` and give the
file a `main()` entry plus the `main().catch(...)` block copied from `scripts/db-reset.ts`.
Reads no command-line arguments and no environment variable directly; the target comes from
`getDevDatabaseUrl()` (which re-asserts the pin) and the destination from
`getBackupDestination()`. Use the `runStep` helper shape from `scripts/db-reset.ts` with a
`[db:backup]` prefix, in this order: assert the development database via
`assertDevelopmentDatabase` over a `pg` `Client`; create the destination directory
recursively; write the data dump by spawning `docker compose exec -T db pg_dump -U recipe_app
-d recipe_dev -Fc` with execa's stdout-to-file redirection (never a shell pipe, and never
piping a custom-format dump into a restore — `pg_restore` requires a seekable file); write the
globals dump by spawning `docker compose exec -T db pg_dumpall -U recipe_app --globals-only`
the same way; collect `postgresVersion` from `SHOW server_version`, `gitCommit` from
`git rev-parse HEAD`, `appliedMigrationCount` from `SELECT count(*) FROM
drizzle.__drizzle_migrations`, and `rowCounts` by enumerating every table in a schema other
than the two catalog schemas and counting each — never a hardcoded table list; then
`writeManifest`. All three filenames share one `compactTimestamp` value:
`recipe_dev-<stamp>.dump`, `recipe_dev-<stamp>-globals.sql`, `recipe_dev-<stamp>-manifest.json`.
The globals dump is only ever copied and hashed as an opaque blob — never read into memory for
inspection, never logged, never quoted in an error message.

**Restore seam (`scripts/restore.ts`).** This task creates only the internal function, not
the CLI. Export a structural interface `ContainerRestoreTarget` with exactly two members —
`copyFilesToContainer(files: Array<{ source: string; target: string }>): Promise<void>` and
`exec(command: string[]): Promise<{ exitCode: number | null; stdout: string; stderr: string }>`
— which a started Testcontainers PostgreSQL container satisfies structurally, so this module
takes no dependency on the testcontainers package and, critically, **has no parameter anywhere
capable of carrying a connection string**. Export `RestoreDumpPaths` (`{ dataDumpPath: string;
globalsDumpPath: string }`) and `restoreIntoContainer(target, dumps, options)` where `options`
carries the in-container user and database name. It copies both dumps into the container, runs
the globals restore first as `psql -v ON_ERROR_STOP=1 -U <user> -d postgres -f <globals>`, then
the data restore as `pg_restore --clean --if-exists --no-owner --jobs 2 -U <user> -d <database>
<dump>`. `--clean` must always be paired with `--if-exists`: unpaired, it returns exit 1 for
objects simply absent from the target, indistinguishable from a real failure. After each call,
throw when the exit code is non-zero, and include the step name and the captured stderr in the
message. Do not add tolerance for an `already exists` error on the globals pass — on a
correctly bootstrapped drill container there is nothing for it to collide with, and tolerating
it here is exactly how a drill reports PASS having never exercised the globals path.

**Tier 1 and tier 2 assertions (`scripts/drill-assertions.ts`).** A standalone importable
module, no module-load side effects, following the `scripts/verify-migration-state.ts` shape.

`assertRowCounts(client, manifest)` — enumerate the restored database's tables the same way
the backup did, require the table *set* to equal the manifest's key set exactly (a table
missing from the restore must fail, not be skipped), and require each count to match. Throw
with a message naming the table and both numbers; table names and row counts are not
credentials and are safe to name.
