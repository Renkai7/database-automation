<objective>
Make a skipped or failing restore drill structurally visible: a committed, machine-readable
record with two independent facts, a hard failure in the default test suite when that record
is missing, red, or stale, and a drill that writes nothing at all when it could not run.

Purpose: BKP-08 is the requirement most easily satisfied on paper and least easily satisfied
in practice. A drill that prints a warning and exits zero is read as a pass by every pipeline
that will ever consume it, and a slow Docker-dependent test inside the default suite is the
one that eventually gets marked skipped to make the suite fast again. Both are closed here
architecturally: the record cannot say "skipped", and the slow test cannot be in the fast
suite.

Output: `docs/restore-drill-status.json`, a `pnpm test` that goes red on stale backup
evidence, and `pnpm test:drill` as the separate slow entry point.
</objective>

## Why this plan cannot share a wave

Beyond the file overlap on `scripts/drill.ts`, this plan's verification runs `pnpm db:drill`,
which reads the single local development database. Plan 02-03's verification writes to it.
Concurrency between them would produce failures with no defect behind them, so every plan in
this phase is serialised.

## Claude's-discretion choices made here

- **Status file path:** `docs/restore-drill-status.json` — committed, machine-readable, and
  sitting next to the runbook it references, which is where a person looking for "is the
  backup evidence current?" will actually look. Phase 7's status view reads this file rather
  than inventing one.
- **Timestamp representation:** full ISO-8601 UTC strings for `lastRunAt` and
  `lastPerformedAt`. The Windows alternate-data-stream trap applies to **filenames**, not to
  JSON values, so a colon is safe here and a parseable timestamp is worth more than an
  artificially compact one. Filenames keep the compact colon-free form.

| Boundary | Description |
|----------|-------------|
| drill process → committed status record | The record is the only durable claim about whether backups work; anything that can write it can make a false claim. |
| status record → default test suite (and, later, Phase 7's status view) | Downstream code makes a go/no-go judgement from this file's contents. |
| drill process → stdout/stderr | The drill handles a globals dump containing a real role-password verifier; anything it prints is read by a human and may be pasted elsewhere. |
