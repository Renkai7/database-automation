<objective>
The owner personally destroys real data and restores it — twice, in two different ways — times
every step, and the runbook is written afterwards from what actually happened.

Purpose: this is the requirement the rest of the phase exists to make possible, and it is the
only one no amount of automation can satisfy. `docs/decisions.md` D7 states it directly:
backup status stays UNKNOWN, never PASS, until a restore has been performed by hand, timed and
documented. An automated drill proves the restore path still works today; only the human drill
proves a person can actually do it under pressure.

Output: `docs/20-restore-runbook.md`, a human fact in the status record set by a person, and
risk R1 finally moved off `never tested`.
</objective>

---

**Act 1 — drop a real table, restore it in place.**

1. Note the current row counts: `pnpm db:query "SELECT (SELECT count(*) FROM recipes) AS
   recipes, (SELECT count(*) FROM ingredients) AS ingredients, (SELECT count(*) FROM steps)
   AS steps;"`
2. Destroy real data: `docker compose exec -T db psql -U recipe_app -d recipe_dev -c "DROP
   TABLE recipes CASCADE;"` — `recipes` is the parent table, and both child tables reference
   it, so this also removes their foreign keys. That second effect is the interesting one.
3. Confirm the damage is real before restoring: re-run the count query and see it fail, and
   list the remaining foreign keys: `docker compose exec -T db psql -U recipe_app -d recipe_dev
   -c "SELECT conname FROM pg_constraint WHERE contype='f';"`
4. Restore: `pnpm db:restore`
5. Confirm the data returned, two ways (D-08). First, compare against the backup manifest: run
   the count query again and check the numbers against the `rowCounts` in the manifest JSON at
   your backup destination, and spot-check a recognisable value with `pnpm db:query "SELECT
   slug, title, base_servings, base_kcal FROM recipes;"`. Second, run `pnpm dev` and open the
   recipe page in a browser — see the seeded recipe render, with its ingredients and steps.
6. Re-run the foreign-key query from step 3 and confirm both constraints came back.

**Act 2 — total loss, restored into a rebuilt cluster.**

7. Destroy the container **and its volume**: `docker compose down -v`
8. Bring up an empty cluster: `docker compose up -d --wait`
9. Restore from both dumps: `pnpm db:restore:cluster`. Read its final line carefully — it
   states whether the globals restore was genuinely exercised or was a no-op because the
   container entrypoint had already created the application role. Whichever it says, that is a
   finding for the runbook.
10. Confirm again the same two ways as step 5.
