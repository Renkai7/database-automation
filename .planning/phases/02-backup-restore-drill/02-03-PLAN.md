## On the `one-way` rating without a `checkpoint:decision`

Task 1 carries `<reversibility rating="one-way">` for D-06 and has **no preceding
`checkpoint:decision`**, deliberately. `02-CONTEXT.md` records the owner making exactly this
choice, with the alternative (`db:restore --target <url>`, allowlist-guarded) named and
rejected in the same breath. The door is already walked through; inserting a checkpoint to
re-ask it is the "gating a decision already made" anti-pattern, and it would flip this plan to
non-autonomous to re-litigate a settled question. The rating stays for the record, so a future
phase reading this plan still sees which door was walked through. `02-01-PLAN.md` carries the
same note for the same reason.

## Why this plan cannot share a wave

`depends_on` lists `02-02` for a reason that is not a file overlap: **the single local
development database is a shared mutable runtime resource.** This plan's verification writes to
it (`pg_restore --clean`, `pnpm db:reset`), while plan 02-02's verification reads it
(`pg_dump` inside `pnpm db:drill`) and compares the result against a manifest taken moments
earlier. Running them concurrently would let a restore land between 02-02's dump and its
assertion, producing a failure with no defect behind it. Every plan in this phase is serialised
for the same reason — the same note plan 01-04 carried in Phase 1.

## A discretion call this plan makes, and why it matters for the runbook

`02-CONTEXT.md` D-07 act 2 exists because "restoring roles into a cluster that already has
them is a no-op". Rebuilding the development cluster with `docker compose down -v` followed by
`docker compose up` does **not** produce a role-empty cluster: the `postgres:17` entrypoint
creates the application role from `POSTGRES_USER` before anything else runs. A strict globals
restore against that cluster therefore aborts on a role collision — the exact failure this
phase's research reproduced live.

Rather than tolerate the collision (which is how a drill reports PASS having never exercised
the globals path) or fail the command outright (which makes act 2 unperformable),
`db:restore:cluster` runs a **pre-flight role check** and states, in words, which of the two
situations it is in. The strict globals restore runs when the cluster is genuinely role-empty;
otherwise the command says so explicitly and points at `pnpm db:drill`, whose disposable
container bootstraps under a non-colliding identity and therefore exercises the globals path
strictly on every run.

**This is exactly the kind of finding D-10 requires the runbook's "what actually happened"
section to carry.** Plan 02-05 must record it there.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| developer/agent → restore CLI | Anything these commands read from their environment or arguments is a lever a future caller can pull. |
