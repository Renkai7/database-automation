<objective>
Make the analyzer look inside the places a dangerous statement can hide. A `DROP TABLE` in a
dollar-quoted `DO` body or a function body is re-parsed and classified exactly as it would be at the
top level, so it reaches the D-02 floor; a `DROP TABLE` that is only text — in a comment, or in a
string being inserted as data — reaches nothing, because it is not a statement.

Purpose: this is phase success criterion 3 in as many words, and it is the half of the analyzer that
`.planning/research/PITFALLS.md` section C1 says a regex could never do. It is also the plan
03-RESEARCH.md flags as carrying its highest implementation uncertainty, so it gets its own plan with
its own fixtures rather than being an afterthought to the top-level classifier.

Output: the recursive inspector with a depth limit, nested findings that say where they came from, and
D-07's unresolvable dynamic SQL enforced at the same floor as the named data-loss operations.
</objective>

Create `src/inspector/inspect-plpgsql.ts`. Export `MAX_NESTING_DEPTH` as 8 — a constant with a comment
explaining that no legitimate migration nests procedural bodies anywhere near that deep, and that a
limit exists so a pathological input cannot exhaust the stack. Export
`extractEmbeddedSql(plpgsqlTree)`, which walks the returned procedural tree and yields every embedded
SQL string it carries. The load-bearing detail, and the one 03-RESEARCH.md Pitfall 2 says is the exact
way this silently fails: the PL/pgSQL tree does not contain further-typed SQL AST nodes — embedded
statements are carried as raw query text. So the traversal collects text, and the recursive step is to
feed that text back through `parseTopLevel`. Design it that way from the start; a traversal written as
if the tree were fully typed passes the obviously-safe case and returns SAFE for the hidden-drop case,
which is the single failure this plan exists to prevent.

Export `inspectPlPgSqlBody(fullStatementSql, sourceContext, depth)` which parses the whole statement —
the entire `DO ... $$ ... $$` block or the entire function creation, not just the dollar-quoted body —
extracts each embedded SQL string, re-parses it through `parseTopLevel`, inspects each resulting
statement with `inspectStatement`, tags each fact set with the given sourceContext and a nestingDepth
one greater than the caller's, and recurses again for any nested DO or function statement found
inside. When depth would exceed `MAX_NESTING_DEPTH`, stop and emit a single fact set with
`statementKind` Unrecognized and a new boolean fact carried on the facts object indicating the limit
was reached, so the outcome is produced by a rule rather than by a special case in code.

In `inspect.ts`, dispatch the DO-block node to `inspectPlPgSqlBody` with sourceContext do-block and the
function-creation node with sourceContext function-body, in both cases also producing the container's
own fact set with statementKind DoBlock or CreateFunction. In `analyze.ts`, flatten container and
nested facts into findings, assigning each nested finding a nestedPath of the enclosing statement
index followed by its position within the body, and keep the existing deterministic sort so a nested
finding always follows its container.

Add three rules to `rules.json`: `do-block-container` and `create-function-container`, both SAFE in
category `usually-safe`, with rationales stating that the container itself is not the hazard and its
body is classified on its own findings — without these two rules D-06 would make every legitimate
trigger-function migration permanently REVIEW REQUIRED, which is exactly the friction D-05 says
manufactures pressure for an override path. And `nesting-depth-exceeded`, BLOCKED in category
`analyzer-integrity`, with a rationale stating that a body the analyzer could not fully read cannot be
called safe.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| dollar-quoted body → recursive parser | The most direct evasion route: text that PostgreSQL will execute but a shallow analyzer treats as a string |
| embedded query text → top-level parser | The re-entry point; a statement crossing it must be classified with exactly the same rules as one written at the top level |
| dynamic execute argument → analysis | Content the analyzer cannot see at all; the boundary where static analysis genuinely ends |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-16 | Tampering | `inspect-plpgsql.ts` | high | mitigate | Embedded SQL is extracted as text and re-parsed through `parseTopLevel`, so a nested statement is classified by the identical rules and reaches the same floor; matched adversarial fixtures assert both the caught and the not-flagged direction |
| T-03-17 | Tampering | dynamic execute | high | mitigate | D-07: an unresolvable argument is BLOCKED and the verdict is enforced by `assertFloorNotWeakened` through `D07_FLOOR_FACTS`, so no rules edit can lower it |
| T-03-18 | Denial of Service | recursion | medium | mitigate | `MAX_NESTING_DEPTH` caps traversal and exceeding it produces a BLOCKED finding rather than a truncated analysis or a stack exhaustion |
| T-03-19 | Tampering | container statements | medium | mitigate | The DO-block and function containers earn SAFE by explicit rule so a legitimate procedural migration is classifiable; without that, the resulting permanent REVIEW REQUIRED is the friction PITFALLS.md section C2 identifies as the start of routine overriding |
</threat_model>

## Flagged Planner Assumptions

- **How far PL/pgSQL recursion goes in practice is Claude's Discretion per 03-CONTEXT.md**, and this
  plan resolves it as: recurse into nested DO and function statements found inside a body, cap at
  depth 8, and treat exceeding the cap as BLOCKED. Exception handlers and nested block labels are
  traversed only insofar as the parser's own tree exposes their embedded SQL text — no separate
  handling is written for them. If a real migration is ever refused because of that, it is a bounded,
  visible false REVIEW or BLOCK, not a silent pass.
- **03-RESEARCH.md assumptions A2 and A4 are unverified until plan 03-01's contract test runs.** This
  plan's task 1 precondition points at that test rather than at the research sketch, so a wrong
  guessed field name surfaces as a failing import rather than as a traversal that quietly finds
  nothing.
