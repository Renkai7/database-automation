`src/types.ts` — the complete public contract, written in full now even though the tracer only
exercises part of it, so plans 02 and 03 can build in parallel against a fixed shape. Export:
`Verdict` as the union `"SAFE" | "REVIEW_REQUIRED" | "BLOCKED"`; `VERDICT_SEVERITY` mapping those to
0/1/2 so "worst wins" (D-10) is one comparison; `StatementKind` as a string union covering
`EmptyInput`, `DropTable`, `DropSchema`, `DropDatabase`, `Truncate`, `DropColumn`, `Delete`, `Update`,
`CreateTable`, `AddColumn`, `SetNotNull`, `DropNotNull`, `AlterColumnType`, `AddUniqueConstraint`,
`AddCheckConstraint`, `AddForeignKey`, `DropConstraint`, `ValidateConstraint`, `CreateIndex`,
`DropIndex`, `RenameColumn`, `RenameTable`, `AlterTypeDropValue`, `CommentOn`, `DoBlock`,
`CreateFunction`, `ExecuteDynamic` and `Unrecognized`; `DefaultVolatility` as
`"none" | "literal" | "immutable" | "stable" | "volatile" | "unknown-function"`; `SourceContext` as
`"top-level" | "do-block" | "function-body"`; `StatementFacts` with the fields `statementKind`,
`schema`, `table`, `column`, `constraintName`, `indexName`, `usingIndexName`, `concurrently`,
`notValid`, `checkProvesNotNull`, `defaultVolatility`, `hasWhereClause`, `dynamicSqlUnresolved`,
`sourceContext` and `nestingDepth` (string-or-null for the name fields, boolean for the flags, number
for the depth) plus an exported `EMPTY_FACTS` constant giving every field its neutral default so
later plans and the floor self-check synthesise complete fact objects rather than partial ones;
`Finding` with `statementIndex`, `nestedPath` (a number array, empty at top level), `verdict`,
`ruleIds` (string array, ascending), `rationales` (string array, same order as `ruleIds`),
`facts`, and `pairedWith` (number or null); `AnalysisResult` with `verdict`, `findings`,
`statementCount` and `rulesVersion`; the error classes `AnalyzerParseError` and `RulesFileError`,
both extending `Error` and setting `name`; and `EXIT_CODES` as a frozen object mapping
`SAFE` to 0, `REVIEW_REQUIRED` to 10, `BLOCKED` to 20, `PARSE_FAILURE` to 30 and `RULES_INVALID` to
40. Comment the exit-code choice: the numbers are deliberately non-adjacent so Node's own generic
exit 1 from an uncaught exception can never be mistaken for a verdict — a crashed analyzer and a
REVIEW REQUIRED migration must not be the same number in the Phase 7 audit record.

`src/inspector/inspect.ts` — `parseTopLevel(sql)` awaits `libpg-query`'s `parse` and returns the
`stmts` array; on rejection it throws `AnalyzerParseError` wrapping `safeErrorMessage(error)` imported
from the repo's `scripts/log.ts`, never a bare re-throw. `inspectStatement(stmt)` returns a
`StatementFacts` built by spreading `EMPTY_FACTS` and overriding what it can observe; for the tracer
it needs only the `DropStmt` case with `removeType` naming a table, setting `statementKind` to
`DropTable` plus `schema` and `table` from the object list. Every other node type returns
`statementKind: "Unrecognized"` for now. No filesystem, no database, no `process.env`, and no work at
import time.

`src/classifier/rules-schema.ts` — the zod schemas (D-03). `FactMatchSchema` is a
`z.record` of fact name to a string, boolean, number, or an array of those: equality and set
membership only, no expressions, per D-01. `RuleSchema` requires `id` (`z.string().min(1)`),
`category` (a `z.enum` of `irreversible-data-loss`, `lock-hazard`, `compatibility`, `usually-safe`
and `analyzer-integrity` — D-04 keeps the rename/compatibility rules a category of their own),
`match`, `verdict` (a `z.enum` of the three verdicts) and `rationale` (`z.string().min(1)`, required
because CI-05 renders the reasoning on the pull request, so "why" has to be structured data).
`RulesFileSchema` requires `version` (`z.number().int()`) and `rules`. Export `parseRulesFile(raw)`
which runs the schema and throws `RulesFileError` carrying zod's own issue list on failure — loudly,
never a partial accept.

`src/classifier/floor.ts` — export `D02_FLOOR_FACTS`, an array of the canonical fact sets for exactly
the operations 03-CONTEXT.md D-02 names: `DropTable`, `DropSchema`, `DropDatabase`, `Truncate`,
`DropColumn`, `Delete` with `hasWhereClause: false`, and `Update` with `hasWhereClause: false`. Each
entry is a complete `StatementFacts` built from `EMPTY_FACTS`. Export `assertFloorNotWeakened(rules,
classifyFacts)` which runs every floor fact set through the *same* `classifyFacts` function real
classification uses — never a duplicated copy — and throws `RulesFileError` naming the offending fact
set and the verdict it produced if any result is not BLOCKED. Note in the header comment that this
covers the "no rule matched" case too, since D-06 would otherwise resolve an unmatched floor
operation to REVIEW REQUIRED.

`src/classifier/classify.ts` — `classifyFacts(facts, rules)` returns every rule whose `match` entries
all hold against `facts` (a scalar matches by strict equality, an array matches by membership). When
several rules match, the most severe verdict wins and all matching rule ids are reported sorted
ascending, so the outcome never depends on the rules' order in the file. When none match, the verdict
is `REVIEW_REQUIRED` with an empty `ruleIds` and a single rationale stating that no rule matched and
SAFE must be earned (D-06). Export `loadRules(rulesFile)` which validates through `parseRulesFile`
and then calls `assertFloorNotWeakened` before returning — the analyzer refuses to start on a
weakened rules file rather than silently substituting the floor.

`src/rules/rules.json` — the tracer seed catalogue: version 1, and one rule per D-02 floor operation
(`drop-table`, `drop-schema`, `drop-database`, `truncate`, `drop-column`, `delete-without-where`,
`update-without-where`), each BLOCKED, each in category `irreversible-data-loss`, each with a real
`rationale` sentence naming the actual hazard. Rule ids are stable hand-assigned kebab-case
identifiers intended to survive catalogue edits, because Phase 7's per-rule override-frequency count
(PROD-04) keys on them. Plan 02 fills in the rest of the catalogue.

`src/analyze.ts` — `analyzeSql(sql, rules)`: parse, inspect each statement into facts, classify each
into a `Finding` with its `statementIndex`, assemble an `AnalysisResult` whose `verdict` is the most
severe finding verdict and whose `findings` array is always complete and never short-circuited on the
first BLOCKED (D-10). It takes SQL text and a loaded rules object as arguments — no filesystem, no
Drizzle knowledge, no database (D-11), so Phase 4's runner can hand it the exact bytes it is about to
execute. Also export `loadDefaultRules()` reading `src/rules/rules.json` through
`resolveJsonModule`-style import or a `readFileSync` relative to `import.meta.url`; keep that helper
clearly separated from `analyzeSql` so the pure function stays pure.

`src/index.ts` — the public barrel re-exporting `analyzeSql`, `loadDefaultRules`, `loadRules` and
everything in `types.ts`.

`src/cli.ts` — reads one or more file paths from the command line, loads the default rules, reads each
file and calls `analyzeSql`, prints a human-readable report (path, overall verdict, then one line per
finding with statement index, verdict, rule ids and rationale) and exits with `EXIT_CODES` for the
worst verdict across all inputs. A `--json` flag prints the `AnalysisResult` array as JSON instead.
File reading and argument parsing live here, not in the core — this is the presentation layer over the
library (D-12). Note in the header comment that accepting a path argument is safe here in a way
02-CONTEXT.md D-06 refused for the restore commands, because this command is read-only and never
