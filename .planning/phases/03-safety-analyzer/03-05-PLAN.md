<objective>
Build the shared corpus D-13 specifies — hand-written `.sql` files plus a committed manifest — and
fill it with the generic, app-agnostic half of the catalogue: every BLOCKED operation, every REVIEW
REQUIRED form, and the explicit USUALLY SAFE set including the three safe-form pairings.

Purpose: the corpus is the artifact two tools consume. Plan 03-07 hands this same directory to
`squawk-cli` unchanged, and Phase 4 inherits it as the regression suite behind the runner. Building it
as files-plus-manifest rather than SQL inlined in test code is what makes that possible.

Output: the manifest schema and harness, and roughly thirty catalogue fixtures whose expected verdicts
are asserted against the real analyzer.
</objective>

Create `test/corpus-manifest-schema.ts`. Keep it separate from `src/classifier/rules-schema.ts`: one
validates policy that ships with the library, the other validates test expectations that do not, and
collapsing them would couple the extractable package to its own test fixtures. Each corpus entry has
`file` (a repository-root-relative path, so a fixture living outside the corpus directory — the two
real Drizzle migrations plan 03-06 adds — can be referenced in place rather than copied and left to
drift), `group` (a zod enum of `catalogue`, `adversarial`, `app-shaped` and `real-migration`),
`expectedVerdict` (the three-verdict enum), `expectedRuleIds` (a string array, allowed to be empty
because the D-06 unmatched case legitimately produces none), `why` (a short non-empty sentence saying
what the fixture is for), and the two optional adversarial fields `pairId` and `half`, the latter a
zod enum of `hidden-executable` and `inert-text-only`, which plan 03-06 uses. Export
`CorpusManifestSchema` and `loadCorpusManifest(path)`.

Seed `test/corpus/manifest.json` with an `entries` array and the three group directories, and write
the first three fixtures so the harness has something real to run against before the bulk arrives:
`blocked/drop-table.sql`, `review-required/set-not-null.sql`, and `safe/create-table.sql`, each a few
lines of ordinary readable SQL. Put no expected verdict, rule id, or classification hint in any SQL
comment anywhere in the corpus, in this task or any later one. D-13 rejected that on principle and the
principle is load-bearing here of all places: this suite's own purpose includes proving comments are
inert, so a comment carrying data the tests depend on would be the exact wrong precedent.

Write `test/corpus.test.ts`. It loads the manifest, loads the default rules once, and for each entry
reads the file, runs `analyzeSql`, and asserts the file verdict matches and that the sorted union of
rule ids across all findings matches `expectedRuleIds` exactly — both a missing expected id and an
unexpected extra id are failures, because the whole point of the manifest is that a fixture's outcome
is pinned rather than approximately right. Failure messages name the file and both values.

Add three structural checks in the same file. First, every `.sql` file found by walking the corpus
directory has a manifest row, and every manifest row's file exists — a fixture nobody asserts on is
worse than no fixture, since it looks like coverage. Second, every rule id in the shipped
`rules.json` appears in at least one manifest row's `expectedRuleIds`, so a catalogue rule that no
fixture exercises fails the suite rather than sitting untested. Allow a small, explicitly enumerated
exception list for rule ids that legitimately cannot appear as an expected outcome, and require a
comment justifying each entry — the exception list must be a deliberate, reviewable decision, exactly
as `tests/guardrails.test.ts`'s own two allowlists are.

Third, the concurrency check: run every corpus entry through `analyzeSql` with `Promise.all`, run the
same set sequentially, and assert the two result arrays are deeply equal. The property being pinned is
that the analyzer holds no mutable module-level state — `loadRules` returns a fresh validated object
rather than memoising a singleton, and the floor self-check runs on every load rather than once per
process — so two analyses in flight at the same time cannot observe each other's half-initialised
state. Phase 4's runner and Phase 5's CI will both call this library more than once per process.

reading this project's older research. Its `why` sentence states that `now()` is catalogued STABLE, not
VOLATILE, and that PostgreSQL's fast metadata-only add-column path applies to any non-volatile default

the review-fatigue anti-pattern the catalogue exists to avoid. Its counterpart, the volatile-default
fixture written in task 2, expects REVIEW_REQUIRED; the two fixtures together are what make the
distinction visible in the corpus rather than only in a unit test.

same unvalidated-then-validate pair where the second statement names a different constraint, expected
REVIEW_REQUIRED, with a `why` sentence stating that exact name equality is required and that a

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| corpus fixture → analyzer | The corpus is the standing adversarial input set; its coverage is what makes a claim about the analyzer's behaviour checkable rather than asserted |
| manifest → test outcome | The manifest is the expectation of record; a row edited to match a wrong result would make the suite green while the analyzer is wrong |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-20 | Tampering | corpus coverage | high | mitigate | The harness fails when a catalogue rule id has no fixture and when a fixture has no manifest row, so coverage cannot silently shrink as rules are added |
| T-03-21 | Repudiation | expected values in SQL comments | medium | mitigate | D-13: no expected verdict lives in any SQL comment; an acceptance criterion checks the corpus files for verdict words in comments, so the suite that proves comments are inert does not itself depend on one |
| T-03-22 | Tampering | shared analyzer state | medium | mitigate | The concurrency check compares a concurrent run of the whole corpus against the sequential run, pinning the no-mutable-module-state property before Phase 4 and Phase 5 call the library repeatedly in one process |
| T-03-04 | Tampering | unmatched operations | medium | mitigate | Two fixtures assert the D-06 default explicitly, including a default calling a function outside the curated volatility table |
</threat_model>
