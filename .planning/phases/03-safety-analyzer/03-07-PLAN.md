disagree about and why. Then close the phase's remaining structural loose ends: bring
`packages/automation/` inside the repository's own guardrail scope, record the phase's decision in the

information — either a rule this catalogue is missing, a rule squawk gets wrong, or a genuine
difference of design worth stating out loud. That examination is phase success criterion 5, and the
report is a deliverable, not overhead.

decision-log entry, and the coverage declaration.

Install with `pnpm --filter automation add -D squawk-cli`, so it lands in this package's
devDependencies and is visibly not a runtime dependency of the library. D-15 makes it a one-time

Write `packages/automation/scripts/squawk-comparison.ts`. It sources its file list from the corpus
manifest so both tools see exactly the same set and nobody has to keep two lists in step. For each file
it records this analyzer's verdict and rule ids by calling `analyzeSql` in-process, and squawk's
findings by spawning the binary with the JSON reporter and the PostgreSQL version pinned to 17 —
matching docs/decisions.md D9's project-wide pin. Without that pin squawk applies its own default
target version, and a version-conditional rule difference would appear in the report as a disagreement
to explain away when it is really a misconfiguration.

Handle squawk's exit code the way this phase's research Pitfall 4 describes: spawn with execa's
non-rejecting option, read stdout and the exit code separately, and treat only unparseable stdout or a
signal-terminated process as a genuine failure. squawk exits non-zero on every file containing a lint
violation, which is most of this corpus by design; a naive try-catch would abort on the first BLOCKED
fixture and silently produce a report covering almost nothing.

The generator emits a markdown table to `docs/30-squawk-comparison.md`: one row per corpus file with
this analyzer's verdict, its rule ids, squawk's rule names, and an agreement column marking each row
agree or disagree. Define agreement explicitly in the report's own preamble, because the two tools do
not speak the same language — squawk emits lint warnings and this analyzer emits a three-tier verdict.
Take agreement to mean squawk flagged a file this analyzer did not call SAFE, or squawk flagged nothing
on a file this analyzer called SAFE. Anything else is a disagreement needing a human sentence.

Use the fixed filename `docs/30-squawk-comparison.md` with no timestamp in the path, following the
existing docs numbering convention, and put the run's timestamp inside the file's content instead. That
is a deliberate choice rather than an accident: `scripts/backup-manifest.ts` records that a raw ISO
timestamp used directly in a filename silently produced a zero-byte file on this machine's filesystem,
so a dated artifact name would need `compactTimestamp` — sidestepping the filename question entirely is
simpler and equally honest.

Add an `analyze:squawk-comparison` script to the root `package.json` invoking the generator through
`tsx`, so the calibration is re-runnable later without anyone reconstructing the command.
