classifier whose verdict depends on none of rule ordering, statement ordering, or identifier spelling.

Create `src/inspector/function-volatility.ts` holding the static curated table. The classifier has no
database connection (D-11), so volatility cannot be looked up from the system catalogue at runtime —
it ships in code. Export three sets and one function. `KNOWN_VOLATILE_FUNCTIONS` contains
`clock_timestamp`, `statement_timestamp`, `transaction_timestamp`, `random`, `random_normal`,
`gen_random_uuid`, `uuid_generate_v4`, `nextval`, `txid_current` and `pg_backend_pid`.
`KNOWN_STABLE_FUNCTIONS` contains `now`, `current_timestamp`, `current_date`, `current_time` and
`localtimestamp`. `KNOWN_IMMUTABLE_FUNCTIONS` holds the small set of genuinely immutable defaults
worth naming, such as `md5` and `length`. `classifyDefaultVolatility(defaultExpressionNode)` returns
`none` when there is no default, `literal` for a constant node or a cast of one, `volatile`, `stable`
or `immutable` for a function-call node whose name is in the corresponding set, and
`unknown-function` for any other function name, including any user-defined one.

The correction this table exists to encode, quoted in 03-RESEARCH.md directly from
postgresql.org/docs/current/sql-altertable.html: PostgreSQL's fast metadata-only add-column path
applies to any non-volatile default, STABLE included, not only to constants. `now()` and
`current_timestamp` are catalogued STABLE, evaluated once at alter time and stored in the table's
metadata exactly like a constant. This project's own earlier research
(`.planning/research/PITFALLS.md` A3 and `FEATURES.md` section 1) groups `now()` with genuinely
volatile functions; that grouping is wrong and must not be carried into the table. Say so in the
module's header comment with the source, so nobody restores it. State plainly what the table does not
know: it is a curated starting point, not a verified-complete catalogue of PostgreSQL's built-ins, and
any function outside it resolves to `unknown-function`, which D-06 already fails safe to REVIEW
REQUIRED rather than SAFE. That failure direction — a false REVIEW, never a false SAFE — is the
property that makes an incomplete table acceptable, and it is the reason the unknown case must never
be widened to a default of SAFE for convenience.

Extend `inspectStatement` in `inspect.ts` to fill the full `StatementFacts` shape for every
`StatementKind` in the union apart from DoBlock, CreateFunction and ExecuteDynamic, which plan 03-04
owns. Discriminate the alter-table node by each sub-command's subtype so add-column, set-not-null,
drop-not-null, alter-column-type, drop-column, add-constraint, drop-constraint and validate-constraint
become distinct kinds rather than one alter-table bucket — an alter table that is really a column drop
must reach the D-02 floor. Split add-constraint further by the constraint's own type into
AddUniqueConstraint, AddCheckConstraint and AddForeignKey, reading notValid from the constraint's
skip-validation flag and usingIndexName from its using-index field. For a check constraint, set
checkProvesNotNull true only when the expression is a null test of the not-null form over a single
column reference, and record that column — this is the fact task 3's third pairing needs, and it must
be derived from the AST node, never from the expression's text. The drop node splits by its remove
type into DropTable, DropSchema, DropDatabase and DropIndex, carrying concurrently for the index case.
Truncate, delete and update map to Truncate, Delete and Update, the latter two setting hasWhereClause
from the presence of the where-clause node. The rename node splits into RenameColumn and RenameTable.
The index node becomes CreateIndex with concurrently and indexName. The create-table node becomes
CreateTable, the comment node becomes CommentOn, and an alter-enum node that removes a value becomes
AlterTypeDropValue. Everything else stays Unrecognized — that is not a gap, it is D-06 working.

Identifier facts carry whatever the parser produced and nothing more. PostgreSQL folds an unquoted
identifier to lower case and preserves a double-quoted one exactly, so the fact value genuinely
differs between the two spellings; that difference is information, not noise to normalise away. No
rule matches on an identifier's spelling, so this can never change a verdict — assert both halves of
that sentence in the test.

Harden `classifyFacts` so its output is independent of the rules file's own ordering: collect every
rule whose match holds, take the most severe verdict among them using `VERDICT_SEVERITY`, and report
all matching ids sorted ascending with their rationales in the same order. Rule ordering inside the
file is therefore not a precedence mechanism, which is what stops a catalogue edit from silently
changing an unrelated verdict — and it is consistent with D-02's "rules may raise severity" rather
than lower it. Keep the D-06 unmatched branch exactly as plan 03-01 wrote it.

Add `applySafeFormPairing(findings)` to `classify.ts` and call it from `analyze.ts` after every
statement has been classified and before the file verdict is computed. The window is one migration
file (D-09) — never a wider set — because the Phase 4 runner executes a file as a unit and must be
able to re-derive a verdict from the SQL in front of it. Implement exactly three pairings, each
matching on facts and on exact name equality:

The unvalidated-then-validated pairing: a finding with notValid true and a constraint name, and a
later finding with statementKind ValidateConstraint carrying the same constraint name on the same
table. Both become SAFE, both record the other's statement index in pairedWith, and both gain the rule
id `pair-not-valid-validated`.

The concurrent-index-then-unique pairing: a CreateIndex finding with concurrently true and an index
name, and a later AddUniqueConstraint finding whose usingIndexName equals it. Both become SAFE, both
record pairedWith, and both gain the rule id `pair-concurrent-index-unique`.

The validated-not-null-check-then-set-not-null pairing: an AddCheckConstraint finding with
checkProvesNotNull true on a table and column, which the first pairing already resolved as validated
in this same file, followed by a SetNotNull finding on that same table and column. The SetNotNull
finding becomes SAFE and gains the rule id `pair-validated-check-set-not-null`. This is the flagship
two-step form from FEATURES.md section 1: the validated check constraint is what lets PostgreSQL 12
and later skip its own table scan, and docs/decisions.md D9 pins the server at 17, so the rules may
assume that behaviour.

Name equality is exact string equality on the fact values, never a fuzzy or case-insensitive match: a
constraint name that differs by one character is a different constraint, and treating it as the same
one would be the analyzer inventing a safe form the migration does not actually contain.

Guard the pairing pass structurally: before lowering any finding, assert that its facts do not match
any entry of `D02_FLOOR_FACTS`; if one does, leave the finding untouched. A pairing that could lower a
floor verdict would be a second route around D-02 sitting inside the classifier itself, which is
exactly the class of bypass the floor exists to remove. Add the three pairing rule ids to `rules.json`
as documentation-bearing entries in category `usually-safe` with verdict SAFE and a rationale naming
the safe form, so Phase 5 can render the reason and Phase 7 can count them like any other rule.

Fix the finding order in `analyze.ts`: sort by ascending statement index, then by nested path
compared element by element, so output is byte-stable across runs and a diff of two reports is
meaningful. Confirm the findings list stays complete — never short-circuited on the first BLOCKED
(D-10) — because Phase 5 renders reasoning on a pull request and a report that hides the second
problem behind the first means fixing one issue and rediscovering the next on the following run.

Write `test/classifier.test.ts` for the severity, ordering, completeness and rule-shuffle behaviours,
and `test/pairing.test.ts` for the three pairings, the near-miss name case, and the floor guard.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| migration SQL text → inspector | Untrusted input authored by an AI agent; every fact this plan adds widens what the analyzer can see about it |
| `rules.json` → classifier | The policy file is itself untrusted input, editable in the same pull request as the SQL it governs |
| pairing pass → verdict | A new code path that lowers severity, and therefore a new potential route around a BLOCKED verdict |
