<objective>
Give the analyzer its two file-facing surfaces without letting either leak into the pure core: a thin
adapter that enumerates the recipe app's real Drizzle migrations against the journal, and a CLI whose
exit codes are a machine-readable verdict rather than a string CI has to parse.

Purpose: D-11 makes the pure-core-and-adapter seam the thing that keeps `packages/automation`
extractable in Phase 7, and D-12 makes the CLI a presentation layer over an importable library rather
than the interface Phase 4's runner would have to shell out to. Both are structural decisions that are
cheap now and expensive to unpick later.

Output: `enumerateMigrationFiles`, the completed CLI with five distinct outcome codes and a `--json`
machine format, and spawned tests proving each code.
</objective>

  <action>
Finish the CLI. Argument handling stays deliberately small: one or more file paths, an optional
`--json` flag, and an optional `--migrations` flag that sources its inputs from
`enumerateMigrationFiles` instead. Accepting a path argument is correct here in a way 02-CONTEXT.md
D-06 refused for the restore commands, and the reason belongs in the header comment: those commands
write to a database and a target argument is the first step toward pointing one at the wrong database,
whereas this command opens no connection at all and only reads text.

Exit-code mapping uses `EXIT_CODES` from `src/types.ts` and nothing else: the worst verdict across all
inputs maps to its code, an `AnalyzerParseError` from any input maps to the parse-failure code, and a
`RulesFileError` maps to the rules-invalid code and is raised before any file is analysed, since a
rules file that cannot be trusted means no verdict can be. Every other error propagates and Node exits
1 on its own, which is precisely why no verdict uses that number.

The human-readable report prints one section per input file: the path, the file verdict, then one line
per finding carrying the statement index, the verdict, the matched rule ids and the rationale. A
verdict never appears without its reasoning, because CI-05 requires the pull request to show the
classification and the reason behind it, and because a report that prints "BLOCKED" alone teaches the
reader to stop reading. Every input file gets its section even when an earlier one was BLOCKED — D-10
forbids short-circuiting, so that fixing one problem does not just reveal the next on the following
run.

The `--json` output is the machine contract Phase 5 renders and Phase 7 records: an array of
`AnalysisResult` objects, each tagged with its source path, serialised whole. Do not trim the findings
list for brevity in either format.

Add `"db:analyze:migrations": "tsx packages/automation/src/cli.ts --migrations"` to the root
`package.json` scripts alongside the existing `db:analyze`, following the `db:*` convention.

Write `test/cli.test.ts` in the shape `tests/restore-cli.test.ts` established: spawn the CLI through

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| filesystem → adapter | Migration files and the journal are read from disk; a mismatch between them is the boundary condition that decides whether a migration was actually examined |
| CLI exit code → CI and audit log | Phase 5 branches on these codes and Phase 7 records them; a collision would silently misreport a verdict |
| command-line arguments → CLI | Paths supplied by the caller determine which files are read |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-11 | Spoofing | CLI exit codes | high | mitigate | Five non-adjacent codes from `EXIT_CODES`, none equal to 1, so an uncaught exception can never be read as a verdict; `test/cli.test.ts` asserts each code against its own fixture |
| T-03-12 | Repudiation | `enumerateMigrationFiles` | high | mitigate | A journal entry with no file, or a file with no journal entry, is a hard error naming the offender — a migration silently not examined must never look like a migration that passed |
| T-03-13 | Tampering | core purity | medium | mitigate | A test asserts no module under `src/inspector/`, `src/classifier/` or `src/analyze.ts` imports a filesystem module, keeping the D-11 seam a checked property rather than a convention |
| T-03-14 | Information Disclosure | CLI report output | low | mitigate | The report prints paths, verdicts, rule ids and rationale only; error text goes through `safeErrorMessage`, and the analyzer holds no credential of any kind since it opens no connection |
| T-03-15 | Tampering | CLI path arguments | low | accept | The CLI runs with the developer's own privileges and reads only what that user could already read; there is no privilege boundary for a path argument to cross, and the command opens no database connection. Revisit if the CLI is ever exposed as a service |
</threat_model>
